# Feishu Calendar Bridge：开发规格 v0.1

**状态：已批准，实施中。本文保留获批时的规格原文；实现进度见[验收状态](./ACCEPTANCE_STATUS.md)。**
日期：2026-09-29  
工作名：Feishu Calendar Bridge；仓库名暂定 `feishu-gcal-bridge`，未检查名称占用。  
配套文档：[社区调研与发布建议](./RESEARCH_AND_LAUNCH.md) · [当前 README](../README.md)

## 1. 决策摘要

做一个小型开源工具：**持续把飞书日程复制到个人 Google 账号下的一个附加日历。** 用户继续在飞书安排工作，在 Google Calendar 和已接入它的工具中查看日程。

用户已在自己的环境中实验过 agent 能读取 Google 附加日历。本规格接受这个使用前提，交付边界放在“Google 中的日程正确、及时”。不增加 agent 适配、MCP 服务或兼容认证工作。

| 项目 | v0.1 决定 |
| --- | --- |
| 源 | 飞书 CalDAV，用户选择一个源日历 |
| 目标 | 个人 Gmail 的 Google Calendar，由工具创建一个专用附加日历 |
| 方向 | 飞书 → Google，单向镜像 |
| 运行方式 | Python CLI；先支持 macOS，用 launchd 定时执行 |
| 更新节奏 | 默认每 120 秒检查一次；正常在线条件下以 5 分钟内可见为目标 |
| 同步内容 | 标题、起止时间、忙闲；提供“仅忙闲”模式 |
| 必须正确的行为 | 新增、改时间/标题、取消、重复日程、全天日程、时区、失败后重试不重复 |
| 其他日历 | 底层采用标准 CalDAV；首版只承诺实测过的飞书支持 |
| 分发 | 自行运行、使用自己的 Google OAuth 客户端；拟采用 MIT 许可证 |

首版不做网站、账号系统、收费、云托管、桌面 GUI、多账号管理、双向同步、会议邀请转发、AI 推理或通用连接器平台。不提供 ICS 订阅服务作为第二条产品路线。

## 2. 为什么这样做

### 2.1 用户要解决的问题

“我的工作会议在飞书，个人日程入口在 Google。只要工作日程能自动出现在 Google，现有的日历工具和 agent 就可以使用它。”

这也是产品的首页叙事。Cue、Muse 可以作为使用场景，但不构成依赖，也不需要专门为它们写代码。用户的附加日历实验是本项目的需求依据，不扩展为对所有 agent、版本、账号的保证。

### 2.2 选择 CalDAV 读取 + Google API 写入

飞书已有 CalDAV 导出实践，能先尝试省去“创建并审批飞书自建应用”的步骤。历史社区报告显示，其目录发现和事件读取存在兼容细节，因此开发重点是把这些细节处理好。[Xuanwo 的实践](https://xuanwo.io/reports/2023-35/) · [Jiajie Chen 的实践](https://jia.je/software/2025/02/04/feishu-dump-calendar/) · [python-caldav 历史问题](https://github.com/python-caldav/caldav/issues/459)

Google 原生“通过网址添加”适合订阅日历，但无法由本工具控制 Google 的拉取时刻。社区存在更新延迟报告；这里不把某个刷新间隔当成 Google 的服务承诺。为满足原始需求中的“及时”，首版主动调用 Calendar API 写入。[Google 订阅说明](https://support.google.com/calendar/answer/37100?hl=en) · [社区更新延迟讨论](https://support.google.com/calendar/thread/254277846/in-which-intervals-does-googe-synchronize-external-calendars?hl=en)

如果实测证明飞书 CalDAV 缺少必要的取消/重复日程信息，先记录限制并报告，再决定是否换成飞书 OpenAPI；不在首版同时维护两套源接入。

## 3. 用户流程与命令

以下命令是待实现的接口约定，当前不能运行。

```sh
fgbridge setup                 # 连接飞书、Google，选择内容，预览并创建镜像日历
fgbridge sync --dry-run        # 显示预计新增/修改/删除数量，不写入 Google
fgbridge sync                  # 完成一次同步
fgbridge status                # 查看最后一次完整成功和错误原因
fgbridge schedule install      # 安装当前用户的 macOS launchd 定时任务
fgbridge schedule remove       # 停止定时同步，保留 Google 已有镜像
```

保持这些入口即可。重新授权或修改配置复用 `setup`，不再做独立管理后台。`--dry-run` 不写 Google，也不推进缺失计数或最后同步成功状态；正常的授权续期可以发生。

### 3.1 首次设置

1. 指引用户在飞书客户端的日历设置中取得 CalDAV 地址和专用凭据。若组织没有开放该功能，明确报出阻塞条件；不尝试绕过组织设置。
2. 交互输入凭据，密码不回显。探测日历列表，由用户选择一个源日历；不默认选中所有共享/订阅日历。
3. 用户提供自己的 Google Desktop OAuth client JSON，浏览器完成个人账号授权。工具检查所需权限，失败时给出可操作的修复说明。
4. 选择“标题 + 时间 + 忙闲”（推荐）或“仅忙闲”。在终端预览少量即将导出的字段；预览不写日志。
5. 创建专用附加日历，默认名 `Feishu`，使用源日历时区。目标 ID 保存后复用；再次 `setup` 不重复建日历。
6. 首次同步完成后显示新增数量、最后成功时间，以及打开 Google Calendar 的入口。
7. 用户安装定时任务后，登录期间每 120 秒运行一次。电脑休眠、关机或网络不可用时不会同步；恢复后补齐当前窗口。

飞书可用、Google 授权和首次同步分别显示结果，避免一个笼统的“连接成功”掩盖失败。设置流程不请求飞书写权限。

### 3.2 停用与清理

`schedule remove` 只停止运行。README 说明如何在 Google 中手动删除专用镜像日历、撤销 Google 授权、撤销飞书 CalDAV 凭据及删除本地凭据文件。首版不增加自动删除整个日历的命令。

目标日历被用户删除后停止写入并提示重新 `setup`，不静默重建。源日历身份或 Google 账号变化时视为重新连接，不把原映射挪给新账号。

## 4. 同步语义：小工具也必须说清楚的部分

### 4.1 范围和历史

- 默认同步过去 7 天到未来 180 天内的实例；边界按源日历时区计算，以时间重叠纳入跨边界事件。
- 该窗口是 v0.1 固定产品行为，不开放大量配置选项。后续有实际需求再调整。
- 已经同步、随后自然落在过去 7 天之外的日程保留在 Google，停止持续校正。它们是历史副本，不保证飞书后来改动旧日程时仍会更新。
- 窗口内的取消或删除需要传播。主动改期后移出读取范围的原占位从当前镜像移除；超出窗口的新时间不补建，进入窗口后再出现。这与历史副本自然老化后保留的规则不同。
- 首版按单个日历、窗口内不超过 2,000 个实例验收。超出时明确失败并跳过删除，不能截断后把缺失部分当成删除。

### 4.2 字段映射

| 飞书/CalDAV 字段 | Google 处理 |
| --- | --- |
| `SUMMARY` | 普通事件映射为标题；仅忙闲模式使用 `Busy` |
| `DTSTART` / `DTEND` / `DURATION` | 保留实际起止时间；全天事件用日期，结束日期采用不包含当天的语义 |
| `TZID` / `VTIMEZONE` | 使用源时区/定义转换；不使用运行机器的本地时区猜测 |
| 浮动时间 | 仅在源日历时区已知时解释；否则该事件报错 |
| `TRANSP` | 映射 Google 的忙闲透明度；不把所有事件强行标为忙碌 |
| `CLASS:PRIVATE/CONFIDENTIAL` | 两种模式下均仅输出 Busy 和时间/忙闲 |
| `STATUS:CANCELLED` | 删除对应镜像；不影响原飞书事件 |
| 重复规则、例外 | 展开为独立的 Google 事件，见 4.3 |
| 地点、描述、参与人、会议链接、附件 | v0.1 不导出；不制造参会人或 Google Meet |
| Google 提醒 | `useDefault=false`，无单独提醒，避免收到两套提醒 |

源中没有标题时使用 `Busy`。CalDAV 未提供 CLASS 时不能据此宣称原日程“公开”：先在开发探测中确认飞书私密日程的实际输出；若不能区分，首版只启用“仅忙闲”，明确说明原因。Google 目标事件统一使用 private 可见性；账号下已获授权的应用仍可能读取选定内容。

源明确标记当前用户已拒绝的邀请时不生成忙碌占位；只有能可靠识别当前用户的参与状态才应用该规则。源缺少信息时沿用导出的忙闲属性，并在探测记录中标明限制。无法确定合法结束时间的异常事件报错，不自行加上 30 分钟等猜测时长。

从“标题 + 时间”切换到“仅忙闲”时，对本安装生成的全部镜像（含历史副本）清除标题信息。这个一次性降级处理必须成功后才显示模式变更完成。反向切换只补充当前同步窗口，历史标题无需追溯恢复。

### 4.3 重复、改期和时区

- 使用现成 iCalendar 解析和重复展开库，不自己实现 RFC 规则解析器。
- 支持日常可遇到的 RRULE、COUNT/UNTIL、RDATE、EXDATE，以及用 RECURRENCE-ID 表示的单次改期、单次取消。
- 身份取自 `源日历标识 + UID + 原始 recurrence-id`；普通事件使用 `UID + single`。标题或修改后的开始时间不是身份。
- 单次改期沿用原始 occurrence 身份，更新已有 Google 事件，避免留下一份旧时间和一份新时间。
- 正确处理跨午夜、跨日全天、夏令时切换和例外实例。遇到不支持的 RRULE/时区/`RANGE=THISANDFUTURE`，标记该系列失败，保留旧镜像；不能猜出一组时间后当作成功。
- 发布前用飞书 UI 实际产生的“仅此日程”“此日程及之后”“全部日程”编辑样本验收。若常见操作尚不支持，应作为发布阻塞，而非让用户自行承担重复日程错误。

Google 日期和事件 ID 约束以官方定义为准。[Events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)

### 4.4 新增、修改、删除的规则

每轮执行：**完整读取源窗口 → 规范化 → 读取目标中的本工具事件 → 计算差异 → 写入 → 记录结果。**

1. 新事件：生成确定性 Google event ID，插入后读回核对；只在成功后记为已同步。
2. 已有事件：比较规范化的导出字段，确有变化才更新；同时检查 Google 中的实际内容。因此即使源没有变，镜像被手工改动也会恢复为源内容。
3. 无变化：零 event 写请求。不因启动次数制造新副本。
4. 缺失事件：在两次连续、完整且成功的源扫描都缺失后，再删除仍属当前管理窗口的镜像。明确的有效取消标记可直接删除。
5. 任一源资源读取或解析失败、分页不完整、访问权限变化、日历 URL 失效、超出上限，都不执行本轮删除。可处理已确认的新增/更新，但整轮状态为 partial。
6. 从非空突然变成全空时，先停止删除并提示重新检查源；经一次明确的 `sync --confirm-empty` 才确认清空，不能把网络故障当成“全取消”。该选项仅处理已成功读出的空快照。
7. Google 中手动创建且没有本安装标记的事件永不修改或删除。目标事件被加入参与人等超出镜像约定的内容时，跳过该事件并报错，避免更新时触发邀请副作用。
8. 镜像事件被手工删除但源仍存在时重新生成；实现中处理 Google 已删除 ID 的 tombstone，不能靠每次随机 ID 重建。

历史副本被手动编辑不持续恢复，符合 4.1 的窗口约定。源只读，所有目标侧改动都不会传回飞书。

## 5. 飞书兼容优化

这是主要开发投入，不扩大为“支持所有日历”。

| 优化点 | 要求 |
| --- | --- |
| 目录发现 | 先按服务响应发现 calendar-home；飞书失败时尝试已知 `/calendars/` 路径并列出候选，不依赖用户手抄 UUID |
| URL 规范化 | 正确处理尾部斜杠、相对 href、转义；不把跨主机跳转自动当成可信地址并携带凭据 |
| 事件读取 | 根据实测选择可用的 calendar-query / calendar-multiget / GET；历史 GET 失败报告需要复核当前库行为 |
| 完整性 | 检查每个 multistatus 项与资源状态，HTTP 207 本身不代表全部读取成功 |
| 时区 | 优先源日历属性和 VTIMEZONE；源时区未知时要求用户明确选择，不能静默套用系统时区 |
| 重复日程 | 使用飞书实际导出样本验证修改、取消和私密属性，fixtures 只保留合成或脱敏内容 |
| 凭据失效 | 区分密码无效、功能未开启、读取被拒绝与网络异常，错误消息给出飞书设置入口 |

这些优化来自历史问题线索，不表示所有问题在当前飞书版本仍然存在。[目录发现案例](https://xuanwo.io/reports/2023-35/) · [GET 失败案例](https://github.com/python-caldav/caldav/issues/459)

## 6. 最小实现结构

### 6.1 技术选择

- Python 3.12+；`caldav` 负责协议、`icalendar` 与维护中的重复展开库负责时间语义、Google 官方 OAuth/Calendar 客户端负责目标写入。
- 精确依赖版本在第一步兼容探测后锁定，检查许可证；不凭当前草案宣布某组合已经可用。
- SQLite 保存安装 ID、源/目标绑定、事件映射、内容哈希、缺失计数、写入意图和最后运行结果。无需 Redis、消息队列或外部数据库。
- 一个 CLI、四个核心职责：读取飞书、转换日程、写入 Google、比较和执行差异。模块以函数/数据结构组合；首版不引入插件注册框架。
- 非敏感配置 TOML；原始 ICS 仅在内存中处理，不默认落盘。数据库也按用户私有文件保护，因标识和时间仍属于个人数据。

示意数据流：

```text
飞书 CalDAV ──只读──> 解析与差异计算 ──Google API──> Google「Feishu」附加日历
                            │                               │
                         本地 SQLite                  用户已连接的日历工具 / agent
```

### 6.2 防重复与恢复

- 安装时生成并保存稳定 installation ID；源 collection 与 UID/实例身份组合生成 source key。
- Google event ID 使用符合 Google 格式的 SHA-256 十六进制结果；private extended properties 保存 installation ID、source key 和映射版本。
- SQLite 在发请求前持久化待执行意图。写入成功但进程崩溃时，重试查询同一 ID 并验证归属，再完成本地提交；409 不自动换随机 ID。
- 对已删除目标 ID，先确认 tombstone，再持久化递增 generation 后生成替代 ID。重试沿用同一个 generation。
- 读目标事件需处理全部分页。更新/删除使用 ETag 条件；412 重新读取后最多重试一次，仍冲突则报 partial。[并发修改官方说明](https://developers.google.com/workspace/calendar/api/guides/version-resources)
- 配置仍在而 SQLite 丢失时，通过目标 extended properties 重建映射；不能先把目标清空。若连 installation ID/绑定也丢失，停止并说明恢复步骤，不猜测接管其他事件。
- 目标 ID 必须为本安装创建并保存的专用日历；拒绝 `primary` 和任意手填目标，避免误用已有日历。

以上只需小型本地持久状态，不做分布式事务系统。[Google extended properties](https://developers.google.com/workspace/calendar/api/guides/extended-properties)

### 6.3 调度与状态

- 使用 launchd 每 120 秒运行一次 `sync`；启动时同步；同一安装用进程锁防并发。
- 429、临时 5xx、网络异常退避重试，遵守 Retry-After，单轮限制重试次数。401 先刷新 token，失败则提示重新 setup；403 区分权限与限流，不一律刷新。
- `status` 展示：源、目标、最后尝试、最后完整成功、数据陈旧时长、本轮增改删数量及最近错误。
- 状态只有 `ok / partial / error / needs_auth / stale`。距最后完整成功超过 10 分钟即提示 stale；无任何成功记录显示“尚未完成首次同步”。
- 部分事件失败不能显示本轮“同步成功”，也不能推进最后完整成功时间。退出码：0 完整成功，1 同步失败/partial，2 配置或授权需处理，3 已有进程运行。
- 日志只记录计数、错误码和不可读的短哈希，不记录标题、描述、账号密码、token、原始 ICS 或含凭据 URL。
- v0.1 不做邮件、机器人通知或监控后台。状态命令和脱敏日志足以支持首批使用者。

## 7. Google 授权与数据处理

请求最小范围：`https://www.googleapis.com/auth/calendar.app.created`。Google 官方将其定义为创建附加日历及管理其中的事件；相关创建/写入操作需要在第一步用个人 Gmail 实测确认。[官方 scope 表](https://developers.google.com/workspace/calendar/api/auth) · [创建日历](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/insert)

不索取整个 Google 日历读写权限，不使用 Workspace 管理员委派，也不用服务账号代替个人登录。桌面 OAuth 使用本机回调、state 和 PKCE；凭据不通过命令行参数传递。

首版先采用用户自带 OAuth client 的开源工具模式。安装指南必须解释 External 应用的 Testing 状态会带来 7 天 refresh token 到期，不能写“设置一次永远可用”。个人自用按适用政策设置发布状态；Production 状态不等于通过 Google 验证，也不保证 token 永不撤销。统一发行的公共 OAuth 客户端及其审核另行决定，不塞进首版。[Google token 生命周期](https://developers.google.com/identity/protocols/oauth2) · [OAuth 政策](https://developers.google.com/identity/protocols/oauth2/policies)

本地凭据放在代码仓库外的用户私有目录，目录权限 0700、文件 0600，更新采用原子替换。macOS 首版采用这一路径即可，不额外开发钥匙串抽象；文档准确写为“本地受文件权限保护”，不宣称加密存储。检查生成文件不被 Git 跟踪。

只有飞书和 Google 必须接收相应请求；无项目方服务器、遥测或公开 ICS URL。用户选择导出的内容会进入 Google，并可能被用户授权的其他应用读取，这是该工具的目的和数据边界。

## 8. 验收标准

下列均为**拟定验收要求，尚无实现或测试结果**。

### 8.1 功能与故障测试

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A1 | 个人 Gmail 首次 setup、再次 setup | 成功创建一个专用附加日历；重复设置不重复创建 |
| A2 | 普通事件新增、改标题、改时间、取消 | Google 结果与窗口内源一致；无旧占位残留 |
| A3 | 同一快照连续运行 10 次 | 只存在一份镜像；无变化时 event 写请求为 0 |
| A4 | 写入成功后、本地提交前强制中断 | 重启自动恢复，未出现第二份事件 |
| A5 | 每周重复、单次改期、单次取消、此后/全部修改 | 对比飞书 UI，实例时间和数量一致 |
| A6 | 全天多日、跨午夜、DST 前后与源/电脑时区不同 | 日期和时间正确，无少一天/多一天/偏移一小时 |
| A7 | 私密事件、缺失隐私信息、模式降级 | 按第 4 节处理；降级后历史副本也没有旧标题 |
| A8 | 读取部分失败、207 中单项失败、窗口超上限 | 状态 partial/error；不触发误删除 |
| A9 | 源凭据失效、源日历消失、突然全空 | 明确报错或需确认；已有镜像不被清空 |
| A10 | 源事件连续两次缺失 | 仅删除对应的本工具事件；目标手工事件保留 |
| A11 | Google 改镜像、删镜像、加参与人 | 按约定恢复/重建/暂停该事件；不发送会议邀请 |
| A12 | Google 429/5xx、token 过期、412 | 有限重试、准确状态；无重复、无把错误算成功 |
| A13 | 丢失 SQLite、两个 sync 同时启动 | 可重建映射；仅一个进程执行写操作 |
| A14 | 电脑休眠、恢复、停用定时任务 | 状态反映陈旧；恢复后补齐；停用后不再写入 |
| A15 | 滚动窗口前后边界及事件移出窗口 | 历史保留与当前删除行为符合 4.1，无无故丢历史 |
| A16 | 日志/仓库文件检查 | 没有凭据、标题、原始 ICS 或真实企业样本 |

自动化测试集中在身份、时间、删除保护、重试和恢复；真实账号使用合成事件验证授权和飞书特有行为。不会把真实会议内容提交到 fixtures。

### 8.2 时效与可用性

- 默认 120 秒轮询；在运行机器在线、无平台限流、源已通过 CalDAV 可读的条件下，新增/修改到 Google API 读回的目标为 5 分钟内；基于两轮缺失确认的删除目标为 10 分钟内。
- 记录“飞书操作时间、首次 CalDAV 可见时间、Google 写入并读回时间”，将飞书导出延迟与本工具延迟分开。不得将这些目标写成已测性能。
- 用不少于 20 次混合新增/修改/取消记录给出实测范围；测试跨度不足时不宣传稳定的 p95 或 SLA。
- 至少连续运行 8 天，覆盖 OAuth Testing 常见的第 7 天问题。Testing 凭据到期应准确报 needs_auth；长期自用配置需另验持续刷新。
- Google UI 和用户现有 agent 作为最终人工查看即可，不建立 agent 测试矩阵或对其刷新速度承诺。

## 9. 开发顺序与工作量

| 顺序 | 交付 | 估算 |
| --- | --- | --- |
| 1. 飞书连接小样 | 获取日历、读取合成普通/重复/私密事件；确认身份、取消语义；个人 Gmail 最小 scope 创建并读写一个测试日历 | 0.5–1.5 个开发日 |
| 2. 同步核心 | 规范化、实例展开、diff、SQLite、防重复、删改和失败状态 | 2–3 个开发日 |
| 3. 可日常运行 | setup/status、launchd 模板和安装/移除、OAuth 指引、真实账号验收 | 1–2 个开发日 |
| 4. 发布准备 | 脱敏测试、README、实测演示、已知限制、版本与许可证 | 0.5–1 个开发日 |

总计约 **4–8 个开发日 + 至少 8 天自然运行观察**，观察可与文档工作并行。这是单人范围估计，不是工期承诺；不包含等待用户登录或组织开启 CalDAV。

第一步若发现飞书常用日程语义无法可靠获得，先返回具体样本、缺失字段及替代成本。没有证据前不悄悄扩大到 OpenAPI、双后端、云服务或更多平台。其他 CalDAV 服务只在有人实际使用并提供脱敏样本时追加适配。
